# PRD · 相册站点改版（导航与布局）

- 版本：v1（讨论稿）
- 日期：2026-02（本轮）
- 作者：产品（AI 代笔，等你拍板）
- 现状代码：`xiaobubuya.github.io`（GitHub Pages，线上 `muyaya.world`）+ `album-api`（Worker）+ `album-studio`（桌面端，加载的是同一个线上前端）

---

## 1. 一句话结论（先看这个）

**问题的本质不是"相册和修图藏得深"，而是"这个站点没有导航层"。**

现在四个页面各自是一个独立小应用，靠一个「⋯」菜单互相串门；三个核心功能
里有两个（相册、修图）在那张菜单的第 2、3 行 —— 手机上「⋯ → 我们的相册」
是**两次点击 + 一次读菜单**，从"看到某张照片想修一下"开始算，是
**四步**（开菜单 → 进相册/修图 → 重新找到那张照片 → 开始干活）。
而且切过去之后**回不到原来的上下文**（照片流滚动位置、正在看的那张、
选中的那批照片全丢）。

所以要做的不是"把入口往前挪一格"，而是补一层导航 + 把三个功能
收进同一个 App 壳里，让它们在**同一个上下文**里互相切换。

## 2. 目标与非目标

### 2.1 目标

| # | 目标 | 可验证的判据 |
|---|---|---|
| G1 | 三个核心功能从任何页面**一步可达** | 桌面/平板顶部导航常驻；手机底部 tab 常驻。"照片 ↔ 相册 ↔ 修图"任意两两切换 ≤ 1 次点击 |
| G2 | 切功能**不丢上下文** | 从照片流进修图、再返回，滚动位置、选中的照片、当前看的那张都还在 |
| G3 | 修图入口**贴着照片** | 大图查看器里直接有「修这张」；照片流支持多选后「批量修图/加入相册」 |
| G4 | 每件"事"只有一个主入口 | 同一个动作不出现两套写法（现在"上传"在照片流、「新建相册」在相册页、两者不通） |
| G5 | 手机上底部不打架 | 页面级 tab 与查看器/幻灯片/修图的"沉浸态"不重叠（沉浸态隐藏 tab） |

### 2.2 非目标（这轮明确不做）

- 不做公开注册、多用户、分享权限体系（现在就是"我们俩 + 口令"）。
- 不做相册的模板/排版重做（那是相册编辑器自己的迭代）。
- 不重写修图引擎（本轮修图只改**入口与布局**，改图能力另立需求）。
- 不做原生 App / PWA 离线包（桌面端仍是 Electron 套壳，不改分发方式）。

## 4. 目标用户与核心场景

用户就是两个人（我 / 老婆），婚纱照 + 日常，手机看得多、电脑修得多。

**场景 A（最高频）**：手机上看照片 → 某张想调一下 → 直接修 → 回到原来位置继续看。
**场景 B**：把这次外拍的照片传上去（手机上，可能几十张）→ 一边传一边挑。
**场景 C（电脑）**：从照片里挑一批 → 排成一本相册 → 调顺序/加说明 → 生成分享链接发亲友。
**场景 D**：修图 App 里连续处理一批照片（导入 → 修 → 导出）。

**关键判断**：A 和 D 说明修图必须是**贴着照片的快捷动作**，不能只是一级页面；
B 说明上传必须能在照片流里就地完成且不打断浏览；C 说明相册是重活，值得一整块工作区。

## 5. 信息架构（IA）

### 5.1 导航模型：一个壳 + 三个 tab + 若干浮层

```
App 壳（导航层，全局唯一）
├── 一级 tab（常驻）
│   ├── 照片   照片流 / 上传 / 大图查看 / 幻灯片
│   ├── 相册   相册列表 → 相册编辑器（选片 / 排序 / 文案 / 分享）
│   └── 修图   修图工作台（打开图片 / 调整 / 导出）
└── 浮层（随时覆盖在任意 tab 上，不属于任一个 tab）
    ├── 登录
    ├── 大图查看器（含「修这张」「加入相册」「分享」）
    ├── 上传队列（不阻塞浏览）
    ├── 幻灯片
    └── 分享链接面板
```

**为什么是三个 tab 而不是把修图做成"照片的右键动作"**：
桌面端是真的要连续修一批（场景 D），那需要一个稳定的工作台；
所以**两者都要** —— 修图是 tab（工作台），也是照片上的快捷动作（带照片跳进去）。

### 5.2 每个 tab 的职责与边界

| tab | 负责 | 不负责 |
|---|---|---|
| 照片 | 看、传、挑、进相册/修图 | 不改照片本身 |
| 相册 | 选片、排序、文案、封面、分享链接 | 不改像素（要改就跳修图） |
| 修图 | 导入、调整、AI、导出 | 不管理相册结构 |

**关键规矩**：跨 tab 的动作一律**带参数跳转**并把上下文存下来
（见 §7），不允许"跳过去让用户自己再找一遍"。

## 6. 布局方案

### 6.1 桌面 / 平板（≥ 900px）：顶部主导航

```
┌──────────────────────────────────────────────────────────────────────┐
│  ◉ 我们的婚纱照   [ 照片 ] [ 相册 ] [ 修图 ]        ＋上传   ⋯  我 ▾ │ ← 64px，常驻
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   当前 tab 的内容（照片流 / 相册网格 / 修图工作台）                  │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

- 导航项用**分段控件**（segment）样式而不是链接文字：三选一的语义更像"视图切换"，
  和现在的 app 内 tab 观感一致，也顺手解决"当前在哪"的可见性。
- `＋上传` 提到顶栏常驻（照片 tab 与相册 tab 都要用），`⋯` 只留设置类
  （幻灯片 / 重新加载 / 退出）。
- 修图 tab 的**工作区仍占满剩余宽度**，右侧面板保持现在这一列（290px），
  面板内部继续用可折叠区（本轮已做）。

### 6.2 手机（< 900px）：底部 tab

```
┌─────────────────────────┐
│  ◉ 我们的婚纱照    ＋ ⋯ │
├─────────────────────────┤
│                         │
│   内容（可滚动）        │
│                         │
├─────────────────────────┤
│  ▣ 照片   ▦ 相册   ✦ 修图│ ← 56px + 安全区，常驻
└─────────────────────────┘
```

- 沉浸态（大图查看 / 幻灯片 / 修图全屏）**隐藏底部 tab**，用返回关闭 ——
  否则 tab 会压在操作栏上（现在 `#viewer` 的底栏就在同一个位置）。
- 修图在手机上仍是"能用但费劲"，不优化到电脑级体验（非目标）。

### 6.3 相册编辑器：左列表 + 右画布（桌面）

```
┌────────────────────────────────────────────────────────────┐
│  ‹ 相册    [标题输入]            已保存 ✓   [分享] [▾工具] │
├──────────┬─────────────────────────────────────────────────┤
│ 照片池   │            相册页面（可上下滚动）               │
│ ☐ ☐ ☐   │   ┌───────────┐  ┌───────────┐                  │
│ ☐ ☐ ☐   │   │  跨页 1   │  │  跨页 2   │                  │
│ （可搜） │   └───────────┘  └───────────┘                  │
└──────────┴─────────────────────────────────────────────────┘
```

现状是"工具面板下拉 + 相册网格"，手机上够用、桌面上浪费宽度。
本轮只做**增量**：桌面显示左侧照片池常驻（手机上仍是下拉面板），
不改相册排序/跨页的核心逻辑。

### 6.4 大图查看器（关键改动）

在底部操作栏加一排"对这张做什么"：

```
        ‹                    [图片]                    ›
┌────────────────────────────────────────────────────────────┐
│ 3 / 128  2024-10-05 14:22   ✦ 修这张   ＋ 加入相册   ⤴ 分享  ✕ │
└────────────────────────────────────────────────────────────┘
```

这一个改动把 P3、P4 一起解决：修图不再需要"先切 tab 再找照片"。

## 7. 跨功能上下文（"不丢上下文"怎么实现）

这是本 PRD 里**技术含量最高**的一条，也是"藏得深"体感的一半来源。

- 把"当前状态"提成一份 **session 状态**，存 `sessionStorage`：
  - `photoStream.scrollY`、`photoStream.selectedIds`、`viewer.id`
  - `album.currentId`、`album.selectedPhotoIds`
  - `studio.lastPhotoId`（从哪张照片进来的）
- 切 tab 时**不重载页面**：改用一个壳 + 三个视图容器（`hidden` 切换），
  这也是 P5（`href="/"` 整页重载）的解法。
- "带照片进修图"走 URL 参数 `studio.html?photo=<id>`：**可分享、可刷新、
  可前进后退**，比纯内存状态可靠（微信里点开链接也成立）。
- 返回时按参数回到那张照片，而不是回到列表顶部。

## 9. 分期（建议按这个顺序，每期都能独立上线）

**P0 · 导航壳（解决"藏得深"，收益最大）**
1. 抽一个共享的导航组件（顶栏 segment + 手机底部 tab）。
2. `index.html` / `album.html` / `studio.html` 接入；去掉各自的重复顶栏。
3. 「⋯」只留设置类；相册、修图从菜单移出。
4. 视图切换不重载 + `sessionStorage` 存滚动位置（先只做滚动位置，最直观）。

**P1 · 照片→修图的直达（解决"断"）**
5. 大图查看器加 `✦ 修这张` / `＋ 加入相册` / `⤴ 分享`。
6. 修图支持 `?photo=<id>` 直接加载。
7. 照片流支持多选（长按/勾选）→ 批量「加入相册」「修图」。

**P2 · 相册编辑器桌面布局**
8. 桌面左照片池常驻 + 右画布（手机保持下拉面板）。
9. 相册里单张照片的「去修图」入口。

**P3 · 打磨**
10. 桌面端窗口内的应用感（隐藏"网页返回"语义、窗口标题跟当前 tab/相册）。
11. 空状态与首次使用引导统一（现在三个空状态的文案风格不一致）。

**每期的硬约束**：新增/改动的交互都要有测试守住（这个仓库的既有规矩：
静态断言 + 真浏览器断言；导航这类"看不见的逻辑"必须用 DOM 断言而不是截图）。

## 10. 风险与取舍

| 风险 | 说明 | 处理 |
|---|---|---|
| R1 | 合成一个壳 = 三个页面变一个页面，体量变大、首屏变重 | 视图按需初始化；修图那条重逻辑（WebGL/面板）在**首次进入修图 tab 时**才初始化 |
| R2 | 会碰到现有测试 | **实测更正**：真正受影响的是 `topbar.test.mjs`（它逐个子元素量 `.st-bar` 的间隙，往里插元素很容易假红 —— 所以导航一律插到 `body`，不动 `.st-bar`）。`autolayout.test.mjs` **不受影响**（它只 require `autolayout.js` 算几何，没有任何 DOM/顶栏断言 —— 本文档早先把它列进来是错的） |
| R3 | 桌面端是 Electron 套壳线上站点，导航一上线，**旧安装包里的 App 立刻变成新导航** | 这正是想要的（不用重打包）；但要注意：如果导航壳改了 `?photo=` 这类深链，老版本 App 也吃得到，所以参数要**向后兼容** |
| R4 | 手机底部 tab 与沉浸态打架 | 沉浸态统一走"隐藏 tab + 顶部/底部返回"。⚠️ **实测发现更要紧的一条**：`album` 的阅读器和 `studio` 都是 `height:100dvh; overflow:hidden`，固定底栏会**压住**内容而不是把内容顶上去 —— 所以 `nav.css` 里对这类页面覆盖了 `height: calc(100dvh - 导航高度)` |
| R5 | 一次全做改动面太大，容易回归 | 按 §9 分期，P0 先只做导航与滚动位置，其余不动 |
| R6 | **静态托管没有服务端路由** | 导航的 href 必须是 `album.html` / `studio.html` 这种带扩展名的真实文件。同一份代码以后如果迁到有重写的托管上，两条都要能走（`currentKey()` 已同时认两种形式） |
| R7 | 分享页是**给没登录的亲友**看的 | 给他们"相册/修图"tab 会误导（点了被弹回登录页）。所以导航支持 `mode:'brand'`，分享页只用这个模式 |

## 11. 三个问题（已拍板 ✅）

1. **手机底部 tab 要不要做？** → **做**。手机是最常用设备，「⋯」→ 相册两次
   点击实在不划算。代价（常驻 56px + 沉浸态处理）接受。
2. **相册保持独立一级页面，还是变成照片流上的筛选视图？** →
   **保持独立一级页面**。相册是要认真排版的"工作区"，独立页 + 编辑器更合适，
   改动面也最小。
3. **修图是否做"从照片带参进入 + 修完返回"的闭环？** → **做**，
   包括 `album-api` 那一侧的"按 id 取单张原图/预览 + 鉴权"。
   这是"用起来断"的根治办法。**归入 P1**（本轮 P0 只做导航层）。

### 11.1 拍板之后记下来的两个副作用

- **修图闭环依赖后端**：`?photo=<id>` 要拿到原图，得先有 `album-api` 的
  单张取图接口。所以 P1 的前半步在后端，不在前端 —— 排期要算进去。
- **旧安装包的 App 会立刻吃到新导航**（它就是套壳线上站点）。
  好处是不用重打包；代价是**任何深链参数都要向后兼容**，
  因为老版本和新版本会同时在线。
