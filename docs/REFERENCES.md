# 参考项目评估

> 2026-09-24。三个外部仓库的评估结论，以及**明确记录哪些实现是独立写的**。

## ⚠️ 先说清楚：本项目现有代码的来源

`studio.js` 里的本地修图工具（锐化 / 暗角 / 颗粒 / 曲线 / HSL）
**全部是独立实现的**，没有参考任何开源项目。用到的都是公开的通用算法：

| 功能 | 算法 | 出处 |
|---|---|---|
| 锐化 | USM（非锐化掩模） | 通用图像处理 |
| 暗角 | 按归一化距离压暗 | 通用 |
| 颗粒 | 哈希噪声 + 亮度调制 | 通用做法 |
| 色调曲线 | Fritsch–Carlson 单调三次插值 | 公开算法（1980） |
| HSL 色相/饱和度 | OKLab（Björn Ottosson, 2020） | 公开算法；**思路受 JixelLight 启发，代码自己写** |
| 亮度系数 | Rec.709 (0.2126/0.7152/0.0722) | 标准 |
| 一键模板 / 分屏对比 / 进度条 | —— | 独立实现，`ai-image-edit` 里没有对应功能 |

这段记录的目的是：以后要对外说明或者开源时，能准确回答"哪部分是自己写的"。

## 评估过的三个仓库

### guihuaxiang1-cmd/pixel-cake

- **定位**：本地 AI 修图（Python + PyTorch + SAM2/LaMa + OpenCV）
- **许可证**：README 写 MIT，**但仓库里没有 LICENSE 文件**（建议让作者补上）
- **技术路线**：后端 Python 跑模型，前端 React + HTTP 调用

**和我们重叠的部分**：去物（我们用火山）、抠人（我们用百度）。他们的
AI 能力靠本地大模型（LaMa ~450MB、SAM2 400MB~2.4GB，要 6GB 显存），
我们的路线是调云端 API —— 各有取舍，不建议换。

**值得参考的**：

| 他们的实现 | 对应用户需求 | 参考价值 |
|---|---|---|
| `radial_adjust` / `linear_adjust`（`enhance.py` 314/341 行） | **我们 roadmap 里的径向/渐变蒙版** | ⭐⭐⭐ 思路直接可用 |
| `local_adjust`（280 行） | 蒙版驱动的局部调色 | ⭐⭐⭐ 和我们现有架构一致 |
| `skin_smooth`（437 行）「中性灰磨皮」 | 本地磨皮（现在走旷视云 API） | ⭐⭐ 思路好，但 WebGL 实现成本高 |
| `_detect_skin`（513 行） | 肤色检测 | ⭐⭐ HSV 范围法，简单可直接用 |
| `apply_makeup` / `teeth_whiten` | 牙齿美白、上妆 | ⭐ 婚礼照可能有用 |

**他们的 `radial_adjust` 思路**（椭圆距离场 + 高斯羽化）：

```
dist = ((X-cx)/rx)^2 + ((Y-cy)/ry)^2
mask = clip(1 - dist, 0, 1)
```

这个 **椭圆归一化距离 + clip** 比我们暗角用的
`smoothstep(0.35, 1.05, r)` 更直观，而且天然支持任意长宽比
（我们的暗角还得额外除 `uAspect` 修正）。做径向蒙版时应该用这个。

**关键洞察**：他们没有为径向/渐变单独写一套调色逻辑 —— 都是
「先生成一个**软掩码**，然后复用同一个 `local_adjust`」。
这正是我们现有架构（`mask` → shader 里 `uUseMask` 混合）的做法，
所以加径向/渐变蒙版对我们来说**只是换一种往位图里填内容的方式**，
不需要动 shader。这条已验证可行。

### snailjayxxx/JixelLight

- **定位**：专业 RAW 后期桌面软件（C++20 + Qt 6.8 + QRhi GPU）
- **许可证**：⚠️ **完全没有许可证声明** —— 默认保留所有权利，
  **不能复制它的代码**。只能看思路，然后用自己的实现。
- **技术路线**：LibRaw 解码 → 线性 ProPhoto 16bit 工作空间 → 多维调色 → ICC 输出

**和我们重叠的部分**：都做 GPU 调色。但他们是 **RAW 显影**方向
（去马赛克、相机矩阵、ICC 色彩管理、宽色域导出），
我们是 **JPG/WebP 成片调色**，场景差别很大，不建议跟。

**⭐ 最有参考价值的部分：感知颜色层（`core/pipeline/ImagePipeline.cpp`）**

他们在 **OKLab** 色彩空间里做色相/饱和度/自然饱和度/8 色 HSL，
而不是在 sRGB 或 YIQ 里。这比我们的 YIQ 近似**明显更准**，
尤其是肤色和复杂色相。

几个可直接借鉴的做法：

1. **OKLab 做色相旋转**：把 (a, b) 当平面向量旋转即可，
   不需要 `atan2` —— 只有做「按色相分区间调」时才需要角度。
   我们目前没有分区间，所以**可以直接在 OKLab 的 (a,b) 平面上转**，
   比 YIQ 准，而且省掉 atan2。

2. **自然饱和度的公式**（`applyPerceptualColor`）：
   ```
   chromaNorm = clamp(chroma / 0.30)
   gain = 1 + vibrance * (1 - chromaNorm) * 0.85
   ```
   已饱和的颜色少动 —— 比我们现在的实现更符合"自然饱和度"的语义。

3. **8 色 HSL 混色器的区间权重**（`hueBandWeight`）：
   ```
   d = hueDistance(hue, center)
   if (d >= 52°) return 0
   return 0.5 + 0.5 * cos(π * d / 52)
   ```
   余弦钟形，±52° 有效范围。做分区间 HSL 时可以直接用这个形状。

4. **5 个可拖动控制点的曲线** —— 和我们曲线的 5 个控制点选择一致
   （我们是 0/.25/.5/.75/1），算是独立验证了这个设计。

5. **`tests/LegacyPipeline.cpp` 保留旧实现做 A/B 对照** ——
   这是个好习惯，比我们的"变异测试"更直接。可以考虑加。

**不值得跟的部分**：RAW 解码、ICC 色彩管理、1024-bin 直方图、
ProPhoto 宽色域 —— 都是专业摄影流程，婚纱相册用不上。

### chunxiuxiamo/ai-image-edit

- **定位**：浏览器里的 AI 修图（Next.js + TypeScript），多模型接入
- **许可证**：MIT（仓库里有 LICENSE，可放心参考）
- **热度**：约 316 stars

**背景**：做"一键人像模板 + 对比滑块 + 进度条"时评估的，
想看看有没有现成的模板表 / 对比交互 / 套索选区可以借。

**结论：复用价值不大。** 三项都没有：

| 想找的 | 他们有没有 | 说明 |
|---|---|---|
| 一键模板（预设参数表） | ❌ 没有 | 模板表最后是我们自己在主进程里定的 |
| 左右对比滑块 | ❌ 没有 | 我们 shader 里一次额外纹理采样就够，比改 DOM 更省 |
| 套索 / 自由选区 | ❌ 没有 | 他们的选区还是矩形框 |

**唯一有点意思的**：他们的编辑结果组织成**图层**（每步一个 layer，
可以单独关掉）。这个思路对 roadmap 的「修图结果回存相册」有启发 ——
不过我们的模型是**非破坏性但线性**的（一次 shader 出图），
要做图层得先改架构，暂时不做。

**净结论**：这次没从它这里拿走任何代码，也没拿走具体算法。
记在这里是为了下次别再评估一遍。

## 结论与建议

| 结论 | 说明 |
|---|---|
| **现有 5 个工具不用改架构** | 独立实现，测试覆盖充分 |
| **HSL 已升级到 OKLab** | 明显更准（尤其肤色），且省掉了 atan2 —— **已落地** |
| **径向/渐变蒙版照 pixel-cake 的思路** | 只换"往位图里填内容"的方式，不动 shader |
| **本地磨皮（中性灰）优先级低** | 思路好但 WebGL 多趟实现成本高；旷视已够用 |
| **⚠️ 不要复制 JixelLight 的代码** | 没有许可证 |
| **pixel-cake 可参考实现，但建议请作者补 LICENSE** | 用了要按 MIT 署名 |
| **ai-image-edit 没有可借的东西** | 已评估，见上 |

**下一步建议顺序**：径向/渐变蒙版（roadmap 已有，成本低）→
液化 / 透视校正（需要网格变形或多趟渲染）。
