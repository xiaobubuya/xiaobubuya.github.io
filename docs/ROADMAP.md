#### 5.1.1 裁剪 / 旋转 / 翻转 —— ⚠️ **已按用户要求重写，旧模型作废**

**先说清楚这一节为什么被推翻**（不然照旧文档改代码会走回头路）。
下面的「排查记录」是**旧模型**下的，它维护的是一条代数等式
（`sX·W0/(sY·H0) == outW/outH`）。用户后来明确否掉了那套：

> "裁剪和翻转做复杂了，不需要做数学运算，裁剪和旋转分开做"
> "不要做运算，就是单纯的度数旋转，不涉及取景框收框，
>  超出取景框范围展示上就是截断即可，把图片缩小后可以正常展示完整"

**现在的模型**（三件互不相干的事）：

| 东西 | 语义 | 谁会改它 |
|---|---|---|
| 取景框 `geom.rect` | 画布归一化 [0,1]，轴对齐 | 拖动 / 比例预设。**旋转角变了它不动** |
| 显示变换 `rot` / `flipX` / `flipY` / `zoom` | 角度、翻转、视野缩放 | 旋转滑杆 / 翻转按钮 / 缩放滑杆。**不动取景框** |
| 视口 | 画布显示的那块源图区域 | `rotatePad(deg)` 随角度撑大，`zoom` 缩放它 |

- 导出 = 取景框那块区域，套上显示变换之后的样子。
- 旋转后原图外面露出的角**不拟合、不收框**，直接显示深色底
  （用户明确接受）。
- `uImgOffset` **恒为 0**：画布显示的是整个视口，取景框只是画在上面的
  一个框，所以"画布坐标 → 图片坐标"除了缩放**没有平移**。
- shader 里只剩一个**标量**缩放 `uDisplayScale`（不是双轴），
  所以"不扭曲"从"靠一条代数等式救"变成**结构性成立**。

**删掉的东西**（禁止再引入）：`inscribedRect` / `fitRatioInRotated` /
`aabbFitsInRotated` / `fitRectToBox` / `currentInscribed` / `viewportAspectFor`。
`test/crop-geometry.test.mjs` 里有一条断言专门守"它们没被重新加回来"。

**这一轮实测抓到 5 个真 bug**（都留了注释和测试）：
1. `uImgOffset` 语义错两轮 —— 先后写成"取景框中心偏移"和"视口原点=
   取景框左下角"。两个错法在**满幅取景框**时都恰好等于 0，
   所以只有把取景框收小才暴露（画面整体偏 0.25）。
2. `draw()` 不接受计划 —— 烘焙时先设 uniform 再 `draw()`，
   而 `draw()` 内部又按 `geom` 重算一次，临时角度被丢掉。
   症状："90° 整转"尺寸对了、内容一点没转。改成 `draw(planOverride)`。
3. 90° 按钮方向反了 —— 符号推了两轮都不对，最后**量了一次**才定
   （两个坐标系各转一次，推导容易自洽地错）。
4. 视口不随角度撑大 → 45° 时"适合窗口"算出 1.0，四角永远深色底。
   正解 `p = |cosφ| + |sinφ|`（也错过两版：撑过头、按外接框宽高比撑）。
5. 面板与 JS 接线（见 5.1.6）。

**测试**：`crop-geometry`（21）/ `rotate-invariant`（15）/ `crop-browser`（9）
/ `crop-ui`（5）。判据从"代数等式"换成"结构性 + 贴边不变量"。

**⭐ 排查记录：「裁剪结果的纵向朝向不对」是怎么找到根因的**

这个 bug 查了很久，**过程本身比结论更值得记**。

现象：取景框取画面**上半**，输出里只有约 1/4 是正确内容，
其余采到了纵向相邻的区块。横向完全正常。

**走错的路（都留着，免得再走）**：

1. **怀疑 `readPixels` 的 y 方向** —— 一度"证明"导出缓冲是对的，
   其实是我把 GL 行序理解反了，属于自我误导。
2. **怀疑符号** —— 四种组合（shader 里 v 取不取反 × offY 取不取反）
   全试过，结果都是"红/混合/蓝"三段、只是顺序不同。
   这个"三段"现象当时被解读成"采样区间大小不对"，其实**两个错误
   同时在**：offY 偏了半个框，以及烘焙时多翻了一次行。
3. **纯代数推理** —— 这是最耗时的。两个坐标系（`crop.rect` 是屏幕约定、
   shader 采样是图片约定）各自都能写出自洽的式子，
   所以"怎么推都推得通"，推理永远收敛不了。

**⭐ 最后管用的方法：不推理，直接量**

做了 `test/_probe-crop-map.mjs`：造一张"绿通道 = 图像行位置"的
**位置编码图**，裁剪后扫输出画布上下两边，把像素解回**采样坐标**，
和公式逐场景比对。一下就看出来：

```
场景            计划 sY/offY      实测采到的 srcV 区间
取画面上半      0.5 / +0.125      [0.375, 0.875]   ← 应 [0, 0.5]
取左上 1/4      0.5 / +0.125      [0.375, 0.875]   ← 应 [0, 0.5]
取右下 1/4      0.5 / -0.125      [0.125, 0.625]   ← 应 [0.5, 1]
```

三行的偏差**符号相反、幅度相同**（都是半个框高），
一眼就定位到 `offY` 的公式。

**真实根因有三个，叠在一起：**

| # | 根因 | 说明 |
|---|---|---|
| ① | `offY` 公式错 | 用了 `-(r.y + r.h/2 - 0.5)*sY`（按**框中心**），应该是 `0.5 - r.y - sY/2`（锚定**框的边** + 用**钳制后**的 sY） |
| ② | `applyCrop` 多翻一次行 | `readPixels` 返回的是自下而上的行序，`ImageData` 是自上而下的，**不抵消**，所以那次翻行是对的 —— 我中间还误删过它 |
| ③ | `cropRenderPlan` 没考虑比例钳制 | 输出画布可能被钳制成目标比例（`applyCropAspect` / `setCropRect` 都会），此时采样区间**必须跟着**缩小，否则画面被拉长 |

**⭐ 三条方法论教训**（比修 bug 更值钱）：

1. **判据必须是"已知答案"，不能是"两处一致"。**
   原来有一条断言是"预览 == 应用后"。这两条路走**同一套 uniform**，
   永远一致 —— 用一致性当判据发现不了朝向错误。
   （我在这上面浪费了最多时间。）
2. **颜色判据太粗，要量"位置"。**
   把 `offY` 换成错的符号，`crop-browser` 那 16 项**全绿** ——
   因为它读的那几个点，两种公式算出来的颜色碰巧一样。
   换成"行编码图 + 断言具体源行"之后就抓得住了。
   ⚠️ 而且**取景框要挑 y 上不居中的**：居中时两种公式完全等价
   （错符号那项被消掉），测试还是瞎的 —— 这一点也踩过。
3. **别跨轮次比较数字。** 第一版探针分好几轮跑，中间改过代码，
   于是"这轮数字"和"上轮数字"混着看，得出过自相矛盾的结论
   （同一个 rect，一次说中心偏 +0.125、一次说偏 −0.25），白绕很久。
   现在的探针一次跑完全部场景。**v1 已删除**，免得后人再去读它。

**现在守它的测试**（两层，各管一段）：

| 测试 | 项数 | 作用 |
|---|---|---|
| `test/crop-geometry.test.mjs` | 15 | 源码级：从 studio.js 里**抠出公式求值**，断言采样区间精确等于取景框那块原图（含"宽高比必须等于输出宽高比"）。快、精确、无魔数 |
| `test/crop-browser.test.mjs` | 16 | 真 Chrome + WebGL：行编码图量**实际采到的源行**；预览与烘焙的朝向；90° 整转的四象限颜色 |

⚠️ 源码级那层是**必须**的：`crop-browser` 对 `offY` 符号是盲的（见教训 2），
只有源码级断言能精确钉住它。反过来，源码级抓不到"烘焙时行序翻错"
（那是另一段代码），要浏览器测试兜。

**已完成五个（锐化 / 暗角 / 颗粒 / 曲线 / HSL）—— 实现要点：**

1. **锐化必须在原始像素上做，而且不能放进 `grade()`。**
   `grade()` 在局部调整时会被调用两次，塞邻域采样进去既浪费
   又会让局部调整的效果变怪。所以它作用在 `main()` 里的源图上。

2. **锐化的步长用原图 texel，不用画布 texel。**
   用画布的话，拖一下窗口锐化半径就变了，预览和导出也对不上。
   代价是屏幕预览时看着比导出略轻 —— 这是两者不一致里代价最小的取舍。

3. **暗角/颗粒放在蒙版混合之后。**
   它们是「整张照片的收尾处理」，不是「某个区域的调整」。
   放进蒙版里的话，涂一小块会让那块的暗角被抹掉，看起来像破了个洞。

4. **暗角的符号：正值压暗（乘 `1 - amt`）。**
   第一版写成 `1 + amt`，结果 0.9 把四角从 128 抬到 **216** —— 越大越亮。
   ⚠️ 这个错误**静态测试抓不到**（它只看有没有 `1.0 - amt` 这个子串），
   是浏览器测试读像素抓出来的。

5. **颗粒要按亮度调制**，否则暗部会浮出一层灰雾（暗部本来就没余量）。

6. **色调曲线用 CPU 生成 LUT，不在 shader 里叠函数。**
   GLSL ES 1.00 没法把一条任意曲线塞进 shader（没有数组构造器），
   用 mix/smoothstep 叠出来的曲线**不保证单调** —— 一旦不单调，
   影调会反转，看着就是坏了。CPU 上可以写真正的单调三次插值
   （Fritsch–Carlson），256 个点、只在滑杆动时算，成本可忽略。

7. **⭐ 曲线的单调约束必须加在「生成控制点」这一步，不是在插值里。**
   实测反例：「中间调+1」把 0.5 抬到 0.65，同时「高光-1」把 0.75
   压到 0.63 —— **控制点本身**先跌再涨。Fritsch–Carlson 保证的是
   「单调数据 → 单调曲线」，数据非单调它无能为力。
   所以生成控制点后要把每个点夹在左右邻居之间（两遍，中间那个点
   受两边夹，一遍不收敛）。

8. **曲线用五个均匀控制点（0/0.25/0.5/0.75/1），不是四个。**
   四个点（0/1-3/2-3/1）时单调插值的端点斜率受限，实测三个滑杆
   **全都主要作用在中间调**（阴影+1 在 @128 抬 19 级，高光+1 也抬 19 级）。
   换五个均匀点之后每个滑杆只动自己那段（+37 / +38 / +30，交叉≈0）。

9. **曲线的 LUT 查表用「加法 + 余量缩放」，不是按比例缩放。**
   按比例（`c *= lut / y`）时纯黑会除以零，加保护之后就正好把
   **褪色最该起作用的像素**漏掉了 —— 纯黑图配褪色实测输出还是 0。
   无脑加法又会让亮饱和色越界、被 clamp 后色相偏移，所以要按剩余
   余量缩一下 delta。

10. **⭐ HSL 的明度不能塞进 YIQ 的 Y。**
    I/Q 是**相对 Y 编码**的色度分量。把「HSL 的 L」当成 Y 用，等于
    换了基准却仍拿旧 I/Q 重建 RGB —— 实测纯红转 30° 后 R 冲到 **242**
    （比原来的 208 还高）。正确顺序：色相/饱和度在 YIQ 里做完，
    **变回 RGB 之后**再按 HSL 的定义推白/推黑。

10. **⭐ HSL 从 YIQ 换成了 OKLab 感知色彩空间。**
    YIQ 是 1950 年代为模拟电视广播设计的，色度平面和人的感知差得
    比较远 —— 在**肤色**（红橙黄那一带）附近尤其明显。婚纱照全是
    肤色，所以这一条很要命。

    OKLab（Björn Ottosson, 2020）的做法是先把线性 sRGB 开立方根到
    近似 LMS 锥体响应，再做矩阵。几个要点：
    - 输入必须是**线性** sRGB，不是 gamma 编码的
    - 色相旋转 = 在 (a,b) 平面上转，**不用 atan2**
      （只有「按色相分区间调」才需要角度；我们没有分区间）
    - 明度直接用 OKLab 的 L（本身就是感知亮度），
      不需要再算 max/min 去凑一个"亮度"
    - 饱和度**正负要分开**：往负（去色）是明确意图，直接等比缩；
      往正（加艳）才需要"已饱和的少动"的保护。
      第一版两边共用一个保护系数，实测 -1 只降约 47%，根本去不了色。

    ⚠️ **已知代价：高饱和色旋转会被 sRGB 色域裁剪。**
    纯红（OKLab 22.7°、chroma≈0.20）转 30° 后超出 sRGB 色域，
    clamp 回来实测只移动了 11.3°；低饱和色（chroma 小）能转满 30°。
    这是 OKLab 的固有性质（感知上转对了，但放不进 sRGB），
    不是代码错 —— `adjust-browser.test.mjs` 里有两条测试分别
    固定这两种行为，免得以后误判成 bug。

11. **测试：给就绪探测和断言都加了超时/快速失败。**
    一条让 shader 编译失败的变异会让页面完全初始化不了，
    26 个用例各等 60 秒 → 整轮 **523 秒**。
    改成：就绪探测用 4 秒超时 + 页面健康前置检查，整轮降到 21 秒。

   再点「复古胶片」（美白 10），两者会叠在一起得到谁也没预期的结果。
   模板应当给出**确定的起点**，不是和现有状态混合。
   `electron-schema.test.js` 里有一条专门守这个（"换模板后参数是干净的"）。

2. **⚠️ 进度条不能编百分比。** 火山即梦的生成时长不可预测（可能 10 秒，
   也可能 90 秒）。第二阶段只显示"已等待多久"，不画一个假装在动的百分比 ——
   编出来的进度条到 99% 卡住比没有进度条更让人焦虑。

3. **⚠️ 分屏对比不能跟「按住看原图」同时开。** 两者都在改"画哪里"，
   同时开的话竖线左边是原图、右边被"按住看原图"整张覆盖，看着像坏了。
   打开分屏会自动关掉按住看原图。

   `uOriginal` 还是 1（整张都是原图），竖线两侧**看起来一样**，

#### 5.1.1b 自动水平校正 ✅（纯本地，不需要 AI）

**用户问的**："把稍微歪的图片自动修正，这个是不是要 AI 能力？"
**结论：不需要。** 这是几何问题不是语义问题 —— 找地平线/垂直边不需要
理解画面内容；本地算得快、不联网、不耗额度，而且**找不到明显直线时
可以什么都不做、只提示**，比"调一次 AI 花了额度还给个错角度"体验好。
AI（百度人脸角度）留作下一步"把脸摆正"，那是另一件事。

**算法**（Hough 式的一维扫描，不是真 Hough 累加器）：

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| 1 | 缩到长边 ~720 | 原图几千万像素没必要全扫；缩略图上噪声被平均掉，更稳 |
| 2 | Sobel 取边缘点 | 阈值取"全局均值×2+8"，纯色图自然被滤掉（点太少 → 返回 null） |
| 3 | θ ∈ ±14°（步长 0.1°）做投影直方图 | 真实直线在**正确角度**上投影能量集中成尖峰 |
| 4 | y' 找水平线、x' 找垂直线，取更尖的 | 地平线和门框/墙角都能用 |
| 5 | 尖峰不明显 → 返回 null | 「没把握就不动作」的出口 |
| 6 | **累加**到当前 `rot` | 用户可能已手调过，自动校正该是"再转正一点"，不是覆盖 |

**两个真 bug（都很有教育意义）**

1. **⚠️⚠️ 漏了长宽比修正 —— 最隐蔽的一个。**
   归一化时 x、y 各自除自己的宽高，于是"归一化空间的斜率"和
   "真实图像空间的斜率"差了 W/H 倍：
   `tan(φ_真实) = (H/W)·tan(θ_归一化)`。
   **正方形时两者才相等** —— 所以这个错在方图上完全看不出来。
   实测 900×600 的照片：真实 1.5° 被报成 2.2°、6° 被报成 9°，
   偏差随角度**规律放大**（看着像"算法不准"，其实是坐标系搞错）。
   修完精度到 **~0.05°**。

2. **扫描范围被长宽比"吃掉"。** ±10° 是**归一化空间**的角，
   3:2 的照片只对应约 ±6.7° 的真实倾斜 —— 真实 8° 的图会被截到 6.7°。
   改成 ±14°（≈ 真实 ±10°）。注释里写明"范围 ≠ 最大可修角度"。

**⚠️ 测试图的坑（和上面那个 bug 长得一模一样，别混）**
第一版合成图是"画正的水平线 + 转整块 canvas"。转出来的四个角会露出
背景色，形成**四条又长又直的边框** —— 那是最强的直线，检测器跑去匹配
它们而不是地平线。表现和"算法不准"完全一样。
改成按**直线方程逐像素画**分界线才对。

**测试**：`test/straighten-browser.test.mjs`（6 项）——
造已知倾斜 φ 的图 → 断言检测结果 ≈ -φ（多角度 + 带噪声）、符号方向、
已正的图不动、纯色图返回 null、点按钮真的设到滑杆上。

#### 5.1.3 ⭐ AI 送图分辨率：别再缩了（这轮最实际的改动）

**改了什么**

| 链路 | 原来 | 现在 |
|---|---|---|
| 美颜（旷视） | 长边缩到 **1600** | **原图分辨率**，超过 4096 才缩 |
| 抠人（百度 labelmap） | 长边缩到 **1024** | 长边 **2048** |
| 结果回写 | 放大回原图 | 通常不需要缩放（送出去的就是原图尺寸） |

**为什么**

美颜的输入是**整张脸**。缩到 1600 再放大回原图 = 皮肤纹理、发丝、
睫毛被重采样两遍，出来明显发糊 —— 而婚纱照就是要放大看的，
这个损失用户一眼能看出来。抠人那边 1024 的蒙版放大回原图时
**发丝和手指边缘会糊成一坨**。

**凭什么敢送原图**（实测，`tools/size-probe.mjs`）：**旷视原样返回输入尺寸**：

```
 800×533   →  800×533
1600×1066  → 1600×1066
4000×2665  → 4000×2665
```

所以送原图不会白费，拿回来的就是原图分辨率的成品。

**代价**（`tools/fullsize-probe.mjs`）：

```
1600px  请求体 0.29MB  → 约 1s
2560px  请求体 0.91MB  → 约 2s
4096px  请求体 1.78MB  → 约 6s
```

而旷视免费额度串行限流本身就要等 ≥3 秒，所以这个增量可以接受。

**为什么仍然留 4096 上限而不是无脑原图**：再大请求体到几 MB，
而返回的图我们本来也要缩回画布尺寸，收益不抵等待；
火山那边对输入尺寸也有自己的限制。

**⭐ 这条是用 Electron 端到端测试守住的**（见下面"测试分工"新增那行）：
把 `MAX_EDGE` 改回 1600、把 2048 改回 1024，两条断言都会红。
这是必要的 —— 一个常数的改动**静态测试完全看不见**。

#### 测试分工（这轮验证出来的经验）

| 类型 | 手段 | 能抓什么 |
|---|---|---|
| 接线 | `adjustments.test.mjs`（静态比对） | uniform 名对不对、顺序对不对、有没有赋值 |
| 数值 | `curve.test.mjs`（纯数学） | 单调性、过冲、串扰、恒等性 —— 不需要浏览器 |
| 断言有效性 | `adjustments-negative.test.mjs`（变异测试） | 上面那些断言是不是装饰品 |
| 算得对不对 | `adjust-browser.test.mjs`（真 Chrome 读像素） | 方向、幅度、边界 —— **静态一律验不出来** |
| 送出去的到底是什么 | `album-studio/test/electron-ai-resolution.test.js`（Electron + 拦 HTTP） | 真正上线的那串字节的尺寸 —— **Chrome 里进不了分支，静态更看不见** |

⭐ **最后一行是这轮新加的一层，值得单独说。** 见下。

**为什么要专门做这一层**

"美颜送的是原图还是缩略图"这件事：

- **静态测试看不见** —— 代码里就是一个 `Math.min(1, 4096 / long)`，
  把 4096 改成 1600 文本上没有任何异常。
- **Chrome 里测不了** —— 没有桌面桥，`hasBeauty()` 返回 false，
  `runBeauty` 弹个提示就 return 了，永远走不到发送那一步。
  （这几条测试一开始就写在 Chrome 的 `template-browser.test.mjs` 里，
  表现是"永远红"，查了很久才发现是**永远进不了分支**。）

**⚠️ 也踩了一个大坑：不能替换 `window.AlbumStudio.megviiBeautify`。**
那个桥是 `contextBridge` 暴露的，**整个对象被冻结**
（`Object.isFrozen === true`，属性 `writable:false configurable:false`）。
在页面里赋值换掉它是**静默失败**的 —— 不报错、不生效，真请求照样打出去。
报出来的错是"旷视密钥被拒 HTTP 401"，**根因完全指不到"桩没生效"**。
（也没法开 `contextIsolation:false`，那是产品安全设置。）

**解法：往下一层走，拦 HTTP。** `test/ai-http-shim.js` 通过
`NODE_OPTIONS=--require` 注进 Electron 主进程，只换掉最外层的 `fetch`：

```
studio.js runBeauty
  → preload 桥 → ipcMain 'ai:beautify'
  → vault 取密钥 → ai-megvii.buildForm（拼 multipart）
  → fetch   ←── 只有这一层是假的
```

然后从捕获到的 multipart / form-urlencoded body 里**解析出图片字节**，
再从 JPEG 的 SOF 段读宽高 —— 这个测量**独立于产品代码**，
产品代码算错了骗不过它。

⚠️ **别用"整个 body 的长度"反推图片尺寸**：body 里还混着
`api_key` / `api_secret` / 各参数的文本，长度和尺寸不成比例。

**有效性验证**（这步不能省）：把 `MAX_EDGE` 改回 1600、把 2048 改回 1024，
两条断言都如期变红，且提示直指"是不是又把 MAX_EDGE 改回 1600 了"。

⚠️ **旁路的 host 白名单漏一个，症状会指错方向**：
`aip.baidubce.com`（百度取 token）第一次漏了，于是那条请求**真的出网**，
拿着假密钥被拒，报"取 token 失败：invalid client_idid"，
看着像密钥问题，其实只是白名单少了一项。


五条硬教训：

- **把暗角的符号取反，静态测试 22 项仍然全绿**，只有读像素那条红了。
- **断言写太松等于没写**：褪色那条本来写 `lut[255] < 255` 又加 `> 200`，
  把"压白位"整个删掉它照样通过。
- **变异测试要跑对文件**：曲线的问题归 `curve.test.mjs`，只跑
  `adjustments.test.mjs` 会"永远抓不到"——不是断言太松，是跑错了文件。
- **变异可能本身无效**：中灰上两种写法输出完全一样时，那条变异测不出东西。
- **⚠️ 别用 RGB 通道差当"饱和度"的指标。** OKLab 的 chroma 是感知色度，
  RGB 三通道极差受色相影响极大（纯红天生就大）。第一版用通道差定阈值，
  判错了实现好坏；换成直接算 OKLab chroma 才准。

### 5.1.4 分享页交付体验（正在做）

> 产品定位上的判断：修图工具是**你们自己用**，分享页是**几十个亲友用**。
> 而分享页一直是全项目最糙的一块 —— 功能类待办（液化、透视校正）
> 的边际价值远低于把这条"给亲友看"的路修好。

#### ✅ 已完成：og 预览（微信转发有图了）

**改造前**：`share.html` 是**静态**文件，**一个 og 标签都没有**。
微信里发链接出去是**一行秃链接**，点开前看不到任何图。

**为什么不能在前端解决**（这是整件事的关键，值得记住）：

> 微信/QQ 的转发爬虫**不执行 JavaScript**，只读原始 HTML 的 `<meta>`。
> 而 `share.html` 在 GitHub Pages 上是静态文件，Worker 碰不到它 ——
> 所以它拿不到"这本相册的封面"，所有相册只能共用一张通用图。

**做法**：新增 Worker 路由 **`GET /s/<token>`**，服务端渲染整页：

- `og:title` / `og:description` 用这本相册的真实标题和页数
- `og:image` 指向 **这本相册自己的封面**（走已有的
  `/api/share/<token>/img/preview/<key>`，它已经按内容寻址做了长缓存）
- 没有封面时退到第一页的第一张照片；都没有才用通用图

**几个必须守住的点**：

1. **og:image 必须是绝对 URL** —— 微信不认相对路径。
2. **标题必须 HTML 转义** —— 它来自用户输入（相册名），
   不转义就能在分享页里注入标签。smoke 里有一条专门的注入用例。
3. **`/s/` 下一个 401 都不能有。** 畸形 token 落到"需要登录"分支会返回
   401，等于告诉访问者"这个路径存在，只是 token 不对"。
   现在所有 `/s/` 前缀都拦在公开段里，一律 404。
4. **不能长缓存** —— 分享可以被撤销，`Cache-Control: max-age=60`，
   并带 `X-Robots-Tag: noindex`（别被搜索引擎收录）。

**链接格式变了**：`api.muyaya.world/s/<token>`
（原来是 `muyaya.world/share.html?t=<token>`）。

⚠️ **老格式仍然可用**，不能让它失效：`share.html` 保留，
它和 `/s/<token>` 读同一份数据、**复用同一个 `reader.js`** ——
阅读逻辑不会出现两份。第 2 步再把前端 `share.js` 收敛掉。

#### ⏳ 还没做：亲友祝福 + 收藏

这是分享页真正缺的**互动层**。婚纱照天然是社交的，而现在分享页只能"看"：

| 功能 | 为什么值得做 |
|---|---|
| **祝福留言**（一段文字 + 名字，**不需要注册**） | 几十个亲友各留一句，是这本相册最不可替代的部分 |
| **收藏 / 点赞** | 让新人知道**哪些照片被喜欢** —— 这是选片时的真实刚需 |

设计要点（避免踩坑）：

- **免注册**：来宾不该为了留一句话去注册。用「相册分享 token + 一次性
  署名」即可，服务端限流防刷。
- **写接口必须有独立的限流**：分享 token 是公开的，任何人都能 POST。
  没有限流就是一个开放的写接口。
- **留言要能删**（新人自己删），否则第一条垃圾留言就毁掉整个页面。
- 数据放 D1（一张 `share_comments` 表），**不放进 R2**（不是图片字节）。

#### ⚠️ 为什么是脚本，不是 DSH 的图像生成插件

DSH 的 `dsh-image-generation` 插件**接不了 Agnes**，三道硬障碍（都实测过）：

| # | 障碍 | 证据 |
|---|---|---|
| ① | 模型白名单写死 | `provider.js` 里 `OPENAI_IMAGES = new Set([...gpt-image-*])`，`agnes-image-*` 永远不在可选项里 |
| ② | 保存要过 `GET /v1/models/{model}`，且返回的 `id` 必须等于 model | Agnes 返回 HTTP 200 但内容是 `{"error":{"code":"model_not_found"}}` —— **没有 id 字段** |
| ③ | 只有 bytedance / openai 两个 provider | `DEFAULTS` 里没有"自定义"这第三个 |

所以插件那条路**不是配置问题，是不通**。脚本直接调 Agnes 的
OpenAI 兼容接口绕开它。

#### ⚠️ 两个必须记住的坑

1. **必须显式传 `response_format: 'b64_json'`。**
   Agnes 默认只回 `url`，而 `b64_json` 字段是**空字符串** ——
   不传这个参数拿到的是 0 长度 base64。
   （DSH 插件恰恰只认 base64，这也是它接不上的原因之一。）
2. **密钥走环境变量 `AGNES_API_KEY`，不写进脚本。**
   前端仓库是**公开**的，密钥写进去就等于公开了。

```bash
$env:AGNES_API_KEY = 'sk-...'
node tools/gen-assets.mjs icons      # 或 og / stage / portrait / all
```

#### ⚠️ 产品素材和验收素材要分开

- `icon-*.png` / `og-cover.png` / `stage-bg.png` 是**产品素材**，进仓库、上线。
- `portrait-test.png` 是**测试素材**：美颜和抠人必须拿有真实皮肤纹理、
  发丝细节的图才测得出来（合成色块测不出"磨皮把毛孔磨没了"）。
  它是 AI 生成的人像，**不是真人**，只用于验收，不进产品页面。
- ⚠️ **相册里的照片不能拿 AI 图替换** —— 那是产品的主体。

守这些素材的是 `test/assets.test.mjs`（11 项），专抓三种**静默失败**：

### 5.2 局部调整增强

- **渐变蒙版**（线性渐变，做天空/地面过渡最常用）
- **径向蒙版**（椭圆，做人像提亮）

### 5.3 修图结果回存相册

现在导出只存本地文件。加「存回相册」的话：
- 内容寻址天然支持非破坏性 —— 改完的图是新 key，原图还在
- 但要想清楚：改完的图算不算"一张新照片"？会不会污染时间线？
  （建议：存成原照片的一个变体，时间线上不单独出现）

### 5.4 火山任务持久化

现在即梦是同步等待（轮询到出图）。关掉 App 任务就丢。

## 明确不做的事

| 事项 | 原因 |
|---|---|
| 安卓 App | 手机上只**看**，不修图。看图用 PWA 就够了 |
| 用户注册 / 多租户 | 就两个人用 |
| 代码签名证书 | 个人自用，Apple 开发者计划 $99/年不值；一次性 `xattr` 能解决 |
| 图片存原图 | 只存 thumb(400w) + preview(1600w)，省空间也够用。修图在 preview 档上做，见下面 ⚠️ |
| 换成自建服务器 | Cloudflare 免费额度完全够，运维成本为零 |

### ⚠️ "修原图"要分两件事说清楚（2026-09-24 澄清）

用户提过「修图能不能都修原图，不要用预览图」。这里有两件**不同**的事，
不要混：

**① AI 送图的分辨率 —— 已经修好了。**
美颜和抠人原来会把图缩到长边 1600 / 1024 再送出去，等于把成品
重采样一遍。现在改成送**当前画布上的原尺寸**（美颜 > 4096 才缩、
抠人 2048）。详见 §5.1.3。

**② 画布上那张"原图"本身是什么档 —— 不是相机原图。**
相册只存 thumb(400w) + preview(1600w)，修图读的是 **preview 档**。
所以：

```
相机原图 6000×4000
   └─ 上传时生成 → preview 1600×1067  ← 修图 App 打开的是这张
   └─ 上传时生成 → thumb    400×267
```

在 App 里点「打开图片」选电脑里的文件时，走的才是**那张文件本身**
（用户要自己保证选的是原图）。但在相册里点「修图」进来的，就是 preview 档。

**这条要改的话代价不小**：preview 档 1600 宽，横构图放大了是够看的，
但如果目标是"打印/大幅面"，就得改上传策略保留原图 ——
而那是 §"明确不做的事"里的决定（省空间和流量）。
**要改的话先想清楚 R2 的存储和流量成本**，不是改一行代码的事。

**③ 界面上别把 preview 档叫"原图"。**
分屏对比那条竖线左边显示的是"未修图的那一版"，也就是 preview 档，
**不是相机原图**。文案上说"原图"会让人以为能对比到相机原始文件，
这一点在跟用户解释时要讲明白。
