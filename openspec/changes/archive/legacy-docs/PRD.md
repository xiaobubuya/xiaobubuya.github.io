## 1. 背景与目标

### 1.1 背景

- 婚纱照目前散落在本地磁盘和网盘，想翻看一次流程很长（开电脑 → 找目录 → 翻文件夹）。
- 旧的相册实现（工作区 `app.js`，1866 行）存在三个结构性问题：
  1. **照片实际是公开的** —— 存在 GitHub `image` 仓库，经 jsDelivr 发布，任何人可绕过页面直接访问。
  2. **鉴权是假的** —— 口令明文写在公开的 JS 里，纯前端字符串比较。
  3. **硬编码凭证** —— 源码里有一个 GitHub PAT（双重 base64 混淆），等价于公开。
- 结论：**不迁移旧代码**，从零重做。

### 1.2 目标

> 手机上打开 `muyaya.world`，能完成三件事：
> ① 流畅翻看全部照片；
> ② 把手机里的照片直接传上去；
> ③ 挑照片、**自由排版**成一页页的相册，左右滑动翻阅。
> 全程只有我们俩能看到。

### 1.3 三个视图的关系（重要）

```
时间线（F2 网格）          全部照片，按拍摄日期自动聚合，只读
      │
      │  挑照片
      ▼
相册（F8）                 手动策展的集合，可自由排版、可翻页
      │
      └── 页面（Page）      固定宽高比的画布，照片在上面自由摆放
```

- **时间线**是"仓库"，回答"我有哪些照片"
- **相册**是"作品"，回答"我想怎么讲这段故事"
- 一张照片可以同时出现在时间线和任意多个相册里

## 2. 用户与场景

### 2.1 用户

| 角色 | 说明 | v1 是否有账号 |
|---|---|---|
| 我（yuge） | 主要用户，也是唯一会做排版的人 | ✅ 口令 |
| 老婆（meimei） | 主要用户，主要看图 | ✅ 口令 |
| 被分享者 | 凭链接看指定相册 | ❌ v1 不做，但架构预留（§4.9） |

> **已定：两人权限完全相同，都能编辑，不区分角色。**
> 因此鉴权层不需要角色判断（`authorize` 的 subject 只带 `name`，用途是审计与提示，不是权限级别）。
> 代价是**并发编辑冲突成为必须处理的问题** —— 见 §F8.2「并发编辑」与 §9 R8。

### 2.2 核心场景

| # | 场景 | 触发条件 | 期望结果 |
|---|---|---|---|
| S1 | 睡前翻看 | 躺床上，单手拿手机 | 打开即看，不等加载，不卡 |
| S2 | 找某张照片 | 记得大概是某个时间段 | 沿时间线滚动能找到 |
| S3 | 沉浸回忆 | 有空闲时间 | 幻灯片自动连播 |
| S4 | **手机里的新照片传上去** | 刚拍完 / 想起有几张没传 | 选图 → 传 → 立刻能在时间线看到 |
| S5 | **做一本相册** | 想整理成有叙事的作品 | 新建相册 → 挑照片 → 自由排版 → 翻阅 |
| S6 | **翻相册** | 想按编排好的样子看 | 左右滑动翻页，像看真相册 |

### 2.3 设备优先级（按用途拆分）

设备的优先级**取决于在做什么**，不是一刀切：

| 用途 | 主要设备 | 次要设备 |
|---|---|---|
| **排版编辑** | **桌面**（鼠标 + 键盘） | 手机 —— 保证能用，不追求好用 |
| 翻看 / 翻页 / 幻灯片 | **手机** | 桌面 |
| 上传（随手补几张） | **手机** | 桌面（可拖拽，但 HEIC 受限，见 §F7） |
| 批量导入 | **桌面本地脚本** | — |

**为什么排版以桌面为主**：自由拖拽需要精确指向。桌面上有鼠标、悬停反馈、方向键 1px 微调，配合吸附对齐，体验相当好；手机上手指遮挡目标、照片变小后四角手柄互相重叠，很难达到同等精度。

**结论**
- **编辑器按桌面优先设计**，移动端只需"能打开、能完成基本调整"
- **所有阅读态（网格 / 大图 / 幻灯片 / 翻页）仍以手机为准** —— 那才是天天会用的场景
- 移动端专有的复杂交互（选中后放大操作区、长按菜单、手势冲突消解）**v1 不做**

- 弱网：4G 下必须可用

## 4. 功能需求

### F1 口令登录

**规则**
1. 用户名为 `yuge` / `meimei`，各自一个口令（只存 Worker 环境变量，**不进前端、不进仓库**）。
2. 前端把口令 POST 给 Worker；校验通过后 Worker 下发 HMAC 签名 Cookie。
3. Cookie：`HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=2592000`（30 天）。
4. 前端不存任何凭证。
5. 连续失败超阈值（10 次 / 15 分钟 / IP）→ `429`。

**验收**
- [ ] 未登录请求任何 `/api/*`（除 login）→ `401`
- [ ] 关标签页 1 小时后重开仍登录
- [ ] iOS Safari 上登录态有效（same-site Cookie 未被当第三方拦截）
- [ ] 连续 15 次错误口令 → 被限流

---

### F2 照片网格（时间线）

**规则**
1. 手机 2 列，桌面 4～5 列；**保持原始宽高比**（不裁方形）。
2. 用 `thumb` 档（长边 400px WebP，约 60KB/张）。
3. 懒加载 + 骨架占位，**避免布局跳动（CLS）**。
4. **行优先**方向保持时间顺序（不能用 CSS `columns`，它会让顺序变成列优先）。
5. 每个日期分组有吸顶标题：`2025年9月18日 · 星期四`。
6. 某天超 100 张 → 默认展示前 30 张，末尾"展开当天全部（N 张）"。

**验收**
- [ ] 手机 4G 首屏（含前 12 张缩略图）< 3s 可见
- [ ] 滚动 500 张不掉帧（无长任务 > 50ms）
- [ ] 加载过程中无明显跳动
- [ ] 顺序严格按 `takenAt` 倒序，跨分组无错乱

### F3 大图查看

**规则**
1. 用 `preview` 档（长边 1600px WebP，约 350KB）。
2. 先显示已缓存的 `thumb`，`preview` 加载完成后无缝替换。
3. 左右滑动切换（在当前分组内循环）；双指缩放用浏览器原生。
4. 右上角关闭，下滑手势关闭。

**验收**
- [ ] 点开 < 500ms 出首帧
- [ ] 滑动切换流畅无白屏
- [ ] 关闭后回到网格原滚动位置

### F7 上传（新增）

**描述**：在手机上把照片传进相册系统，传完立即可在时间线看到。

**入口**
- 时间线右上角「＋」
- 相册编辑页的「添加照片」
- **桌面：把文件 / 文件夹直接拖进页面**（见下"桌面端路径"）

**核心流程**

```
选图（可多选）
  → 逐张在浏览器端解码 + 生成派生图
      ├─ thumb   长边 400px  WebP q75
      └─ preview 长边 1600px WebP q80
  → 三个文件各走 presigned PUT URL 直传 R2（不经 Worker）
  → 通知 Worker 登记元数据（写 manifest）
  → 时间线出现新照片
```

**规则**
1. **浏览器端生成派生图**，不依赖服务端算力：
   `createImageBitmap(file)` → `OffscreenCanvas` 缩放 → `convertToBlob({type:'image/webp', quality})`
2. 三档（thumb / preview / 原图或 full）**并行上传**，各自独立重试。
3. **去重**：上传前先算 `sha256(原图)` 前 16 位；已存在则整张跳过，不重复占用空间。
4. **进度**：逐张显示状态（等待 / 上传中 x% / 完成 / 失败）。失败可单张重试。
5. **断点**：上传队列持久化到 IndexedDB；中途关页面，重开可续传。
6. **元数据**：从文件里读 `takenAt`（EXIF `DateTimeOriginal`，缺失则用文件修改时间），生成 `w`/`h`。
7. **并发**：最多 3 张并行，避免占满上行带宽把界面拖死。

**桌面端路径**

手机是主要的上传来源，但桌面也要能用 —— **尤其是排版，桌面体验明显更好**（§2.3）。

1. 支持从文件管理器**拖拽多个文件**到页面任意位置上传；拖拽时整页高亮提示。
2. 支持**拖入文件夹**（递归取图）。
3. 走同一套链路（浏览器端派生 → presigned 直传 → 登记），不另写一份逻辑。
4. **桌面 Chrome / Edge 无法解码 HEIC** —— 这是桌面路径的主要缺口，见下方"边界与兜底"。
   若你以后主要在桌面导入，**直接用本地批量脚本更快**（`ALBUM-PLAN.md` §3.4），它能处理 HEIC 且不占上行带宽分片。
5. 拖拽上传同样受"最多 3 张并行"约束，避免把上行打满。

**边界与兜底**
- **浏览器无法解码该格式**（典型：桌面 Chrome / 部分安卓打不开 iPhone 的 HEIC）：
  → 只上传原图，标记 `derivativesPending: true`，该照片在时间线显示占位 + "处理中"角标；
  → 由本地批量脚本或定时任务补生成派生图（见 §9 R5）。
- **单张超大（> 100MB）**：拒绝并提示，避免占用上行过久。
- **非图片文件**：直接过滤。
- **上传中锁屏 / 切后台**：暂停队列，回到前台自动继续。
- **存储额度接近上限**：上传前检查，超过阈值先警告。

**验收**
- [ ] iPhone 相册里选 10 张 HEIC，能全部传成功并在时间线看到
- [ ] 同一张图传两次，第二次被识别为重复并跳过
- [ ] 上传 10 张过程中杀掉页面，重开能续传未完成的部分
- [ ] 单张失败可单独重试，不影响其他张
- [ ] 4G 下传 10 张（约 80MB）能在合理时间内完成且界面不卡死
- [ ] 传完的照片方向正确（EXIF 旋转已处理）

#### F8.2 自由排版编辑器（核心，最高风险）

**描述**：在一张固定宽高比的画布上，**像素级自由摆放**照片。

**排版数据模型**（归一化坐标，与屏幕无关）

```json
{
  "canvas": { "ratio": 1.5, "bg": "#ffffff" },
  "items": [
    {
      "id": "it_01",
      "photo": "a1b2c3d4e5f60718",
      "x": 0.05, "y": 0.10,
      "w": 0.40, "h": 0.55,
      "rot": -3,
      "z": 1,
      "fit": "cover",
      "radius": 0.01,
      "caption": "第一次见面"
    }
  ]
}
```

**关键设计决策：坐标归一化到 0～1。**
同一个 JSON 在任何屏幕上等比渲染 —— 编辑器所见即读者所得，两端共用一个渲染器。画布宽高比由 `canvas.ratio` 决定，竖版/横版/方版都只是换一个数字。

**编辑操作**

| 操作 | 手势 / 方式 |
|---|---|
| 添加照片 | 底部素材托盘点选；或从托盘拖到画布指定位置 |
| 移动 | 单指拖动照片 |
| 缩放 | 拖动四角手柄 |
| 旋转 | 拖动顶部旋转手柄 |
| 调整层级 | 选中后「置顶 / 上移 / 下移 / 置底」 |
| 删除 | 选中后「删除」，或拖到画布外的回收区 |
| 换图 | 选中后点「替换」，从托盘选新图 |
| 图注 | 选中后输入文字（可关） |
| 撤销 / 重做 | 顶部按钮，至少 20 步 |
| 换画布比例 | 画布设置里切换（3:2 / 4:3 / 1:1 / 2:3） |
| 翻到另一页 | 编辑器内的页面缩略条 |

**⚠️ 可用性设计（桌面优先，移动端保证可用）**

排版以**桌面**为主（§2.3）。下表区分"必须"与"不做"，避免在移动端专有难点上过度投入：

| # | 措施 | 优先级 | 原型状态 |
|---|---|---|---|
| 1 | **手势隔离**：编辑态禁用页面滚动 | 必须 | ✅ |
| 2 | **手柄命中区 44×44pt**（视觉 12px，透明撑开） | 必须 | ✅ |
| 3 | **手指/指针遮挡补偿**：按位移量拖动，不跳到指针中心 | 必须 | ✅ |
| 4 | **吸附对齐 + 参考线**：画布四边/中线 + 其他照片的边缘与中心 | 必须 | ✅ |
| 5 | **旋转回正**到 0°/±90° | 必须 | ✅ |
| 6 | **自动保存**：debounce 1s 写 D1，带 `baseVersion` 做乐观并发；标题栏显示状态 | 必须 | ✅（模拟） |
| 7 | **桌面增强**：悬停反馈、光标语义、方向键 1px / Shift 10px 微调 | 必须 | ✅ |
| 8 | 手机竖屏时提示横屏（不强制） | 尽力 | ✅ |
| 9 | 离开时有未保存改动则二次确认 | 尽力 | ⬜ |
| 10 | **小手柄冲突消解**（照片很小时四角手柄重叠） | **v1 不做** | ⬜ |

> 第 4 条在**两端都是关键** —— 没有吸附，纯手拖出来的相册一定歪七扭八。
> 第 10 条是移动端专有难点，桌面优先后不再是核心路径，延后处理。

**并发编辑（两人权限相同，都能改）**

两人都能编辑且不分角色（§2.1），所以必须处理"同时改同一页"。
**采用乐观并发，不用编辑锁。**

流程：

1. 编辑器加载某页时，记下该页当前的 `version`
2. 自动保存请求体带 `baseVersion`
3. Worker 校验：`baseVersion !== 当前 version` → 返回 **409**，并附上服务端当前排版
4. 前端收到 409 → **立即停止自动保存**，弹提示：

   > 这一页在别处被改过了。
   > 「用我的版本覆盖」　「查看对方的版本」　「取消」

5. 选「覆盖」→ 用服务端最新 `version` 重试一次写入
6. 选「查看」→ 切换预览两份排版，再由用户决定
7. 选「取消」→ 放弃本地未保存改动，加载服务端版本

**为什么不用编辑锁**：两人很少同时在线，锁会带来"锁没释放"的过期问题，还要维护心跳与超时回收。乐观并发的实现成本只有一个整数列 + 一次比较，**而且不会静默丢改动**。

**关于"静默覆盖"**：v1 明确**不做**最后写入者覆盖。排版是手工劳动，丢掉一次可能就是一小时，必须让用户知情。

**顺带**：`updated_by` 记录最后编辑者，相册列表可显示"meimei 刚改过"，减少无谓的互相覆盖。

**验收**

桌面（主要）：
- [ ] 鼠标能完成：加图 → 移动 → 缩放 → 旋转 → 调层级 → 保存，全程无需键盘
- [ ] 方向键移动 1px / Shift+方向键 10px，且连续按键合并为一步撤销
- [ ] 照片靠近画布边缘/中线/其他照片时出现参考线并吸附
- [ ] 撤销能连续回退 20 步
- [ ] 排版结果与阅读态渲染**像素级一致**（同一 JSON）
- [ ] 中途强制关闭标签页，重开能恢复到最近一次自动保存
- [ ] **并发冲突**：两个浏览器同时打开同一页，A 保存后 B 再保存 → B 收到 409 提示，**不静默覆盖 A**
- [ ] 冲突提示选「用我的版本覆盖」能正确写入；选「取消」能加载回服务端版本

手机（次要，保证可用）：
- [ ] 能打开编辑器并完成基本的移动 / 缩放 / 保存
- [ ] 拖动照片时页面不跟着滚动
- [ ] 手柄能被点中（照片占画布 40% 以上时不失误）
- [ ] 缩放到很小时操作困难属**已知可接受**（第 10 条不做）

#### F8.3 翻页阅读器

**描述**：像翻真相册一样逐页看。

**规则**
1. **横滑切换**（已定），一页一屏。
2. 页面按 `canvas.ratio` 等比铺满可视区，留白居中。
3. **预加载相邻页**，保证滑动跟手。
4. 点击屏幕中央 → 显示/隐藏控制层（页码、返回、全屏）。
5. 页面右下角显示 `3 / 12`。
6. 支持从相册封面直接进入阅读。
7. 也支持"连续滚动"模式作为备选（长按或设置里切换），适合快速浏览。

**验收**
- [ ] 滑动切页跟手，无明显延迟
- [ ] 快速连滑 10 页不崩、不白屏
- [ ] 排版结果在手机 / 桌面渲染一致（等比缩放）
- [ ] 预加载生效：滑动到下一页时图片已就绪

### F9 分享链接（v1.5，v1 只做架构预留）

**为什么 v1 就要预留**：如果 v1 把权限判断写死成"是登录用户就全放行"，v1.5 加分享时就得重构鉴权与图片访问链路。**预留成本几乎为零，返工成本很高。**

**v1 必须满足**
1. Worker 内部把权限判断抽象为 `authorize(subject, resource)`：
   - v1 的 `subject` 只有 `{ kind: 'user', name }`
   - v1.5 增加 `{ kind: 'share', tokenId, scope }`
2. 图片访问走 `authorize` 的结果，而不是"登录状态"这个具体概念。
3. 数据模型预留 `share_tokens` 表（§6.3），v1 不写入数据。

## 6. 数据模型

### 6.1 照片索引（D1 `photos` 表）

> **Q7 决策：从 R2 的 `manifest.json` 改为 D1 表。**
> 原因有二：① 浏览器上传与本地批量脚本都会写索引，放单个 JSON 文件**并发写会丢照片**（R9）；
> ② 3000 张时单文件已近 400KB，每次列表都要整体下载。
> 放 D1 后按行 upsert 天然原子，且支持真正的分页与排序。

```sql
CREATE TABLE photos (
  k           TEXT PRIMARY KEY,           -- sha256(原图).slice(0,16)，内容寻址
  w           INTEGER NOT NULL,
  h           INTEGER NOT NULL,
  taken_at    TEXT NOT NULL,              -- ISO8601
  has_full    INTEGER NOT NULL DEFAULT 0,
  pending     INTEGER NOT NULL DEFAULT 0, -- 派生图待补（HEIC 等）
  bytes       INTEGER,
  uploaded_by TEXT,
  created_at  TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX idx_photos_taken ON photos(taken_at DESC);
```

- `k` = `sha256(原图).slice(0,16)` —— 内容寻址，天然去重
- 不含 EXIF GPS 等敏感字段
- 写入统一走 `INSERT ... ON CONFLICT(k) DO UPDATE`，**并发安全** —— R9 由此消解
- **R2 只存图片字节，不再存索引**

**分页用游标，不用 OFFSET**（大偏移会越翻越慢）：

```sql
SELECT * FROM photos WHERE taken_at < ? ORDER BY taken_at DESC LIMIT 60
```

日期分组由前端就返回结果就地分桶，不额外查库。

### 6.2 图片档位

| 档位 | 规格 | 用途 | v1 |
|---|---|---|---|
| `thumb` | 长边 400px WebP q75 | 网格 / 编辑器托盘 | ✅ 必需 |
| `preview` | 长边 1600px WebP q80 | 大图 / 幻灯片 / **相册渲染** | ✅ 必需 |
| `full` | 长边 2560px JPEG q85 | 下载高清原图 | ❌ **v1 不生成**（Q2 已定） |

> **Q2 决策：v1 不生成 `full` 档。** 理由：v1 的定位是"看图 + 排版"，不需要下载原图；
> 原图本来就有本地 + 网盘冷备；而多一档会让每张上传量增加约 1.2MB，明显拖慢手机上传。
> **上传脚本保留 `--with-full` 开关**，日后想补可增量补传（内容寻址，不会重复）。
> 对应地，F3 的"下载原图"入口在 `has_full = 0` 时**不显示**。

### 6.3 D1

```sql
-- 登录限流
CREATE TABLE login_attempts (ip TEXT NOT NULL, ts INTEGER NOT NULL);
CREATE INDEX idx_login_attempts ON login_attempts(ip, ts);

-- 相册
CREATE TABLE albums (
  id          TEXT PRIMARY KEY,
  title       TEXT NOT NULL,
  cover_key   TEXT,
  page_count  INTEGER NOT NULL DEFAULT 0,
  sort_order  INTEGER NOT NULL DEFAULT 0,
  created_at  TEXT NOT NULL DEFAULT (datetime('now')),
  updated_by  TEXT,
  updated_at  TEXT NOT NULL DEFAULT (datetime('now'))
);

-- 相册页面：layout_json 存 §F8.2 的归一化排版数据
CREATE TABLE album_pages (
  id           TEXT PRIMARY KEY,
  album_id     TEXT NOT NULL REFERENCES albums(id) ON DELETE CASCADE,
  page_index   INTEGER NOT NULL,
  layout_json  TEXT NOT NULL,
  version      INTEGER NOT NULL DEFAULT 1,   -- 乐观并发：每次成功写入 +1
  updated_by   TEXT,                          -- 'yuge' | 'meimei'
  updated_at   TEXT NOT NULL DEFAULT (datetime('now')),
  UNIQUE(album_id, page_index)
);
CREATE INDEX idx_album_pages ON album_pages(album_id, page_index);

-- v1.5 用，v1 建好不写
CREATE TABLE share_tokens (
  id          TEXT PRIMARY KEY,
  scope_json  TEXT NOT NULL,
  created_at  TEXT NOT NULL DEFAULT (datetime('now')),
  expires_at  TEXT NOT NULL,
  revoked     INTEGER NOT NULL DEFAULT 0
);
```

**为什么排版存 D1 而不是 R2**：排版会被频繁小改（拖一张照片就变），需要按页 upsert；R2 对象是整体替换，不适合。单页 JSON 通常 < 2KB，D1 完全够。**照片本身仍在 R2，D1 只存归一的排版坐标。**

> 旧版的 `wishes` / `events` / `favorites` 表 v1 不建（功能已砍）。

## 7. Worker API

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/login` | 口令 → 签名 Cookie |
| POST | `/api/logout` | 清 Cookie |
| GET | `/api/photos` | 游标分页（`?cursor=<taken_at>&limit=60`），按 `taken_at` 倒序 |
| GET | `/api/photos/days` | 日期分组索引（每天日期 + 张数），供时间线吸顶标题与跳转 |
| GET | `/api/img/:size/:key` | 鉴权 → 302 到 R2 短过期签名 URL |
| POST | `/api/upload-url` | 签发 presigned PUT（单文件） |
| POST | `/api/photos/register` | 上传完成后登记元数据 |
| GET | `/api/albums` | 相册列表 |
| POST | `/api/albums` | 新建相册 |
| PATCH | `/api/albums/:id` | 改名 / 换封面 / 排序 |
| DELETE | `/api/albums/:id` | 删除相册（级联删页面） |
| GET | `/api/albums/:id/pages` | 全部页面（含 layout_json） |
| PUT | `/api/albums/:id/pages/:index` | upsert 单页排版（自动保存用）；请求体带 `baseVersion`，版本不符返回 **409** + 服务端当前排版 |
| POST | `/api/albums/:id/pages` | 新增页 |
| DELETE | `/api/albums/:id/pages/:index` | 删除页 + 重排 index |

统一中间件：验签 → 过期检查 → 失败限流 → CORS 白名单 → 路由。
